### 3. s04：找地点、加地点，以及两套 add_visit

你的判断成立：“找一个博物馆”首先应展示候选，不能直接算作已经加入行程。当前后端的 add_visit 本身是在构造提案；真正让它变成直接新增的是前端的自动 adopt。模型生成的候选推荐不等于用户选择。

建议先复用现有候选、Pending 和 Adopt，不急着新增一套搜索命令：

- “找一个……”显示候选和“加入行程”；Draft 保持原样。
- “加一个……”也先把具体地点候选展示出来，用户确认后采用。
- 后续“换第二个候选”只更新 Pending；不能修改已采用的 Draft。
- 硬性营业条件未证实时，可以展示候选，但不能把它说成满足条件的正式结果。

两个 add_visit 分属不同表示：`semantic_segments` 中的 operation 记录理解到的操作意图；`commands.add_visit` 提供执行所需的查询条件、顺序和目标。代码最终把 commands 编译为本地 actions。真正驱动候选检索的是后者，operation segment 不会再执行一次。

`preferred_add` 是给 Preferences 的受限主题列表加项，用于后续上下文及部分排序；`notes_add` 保存无法完整执行或验证的文字要求，会传给后续模型并显示提示。代码没有 `node_add`。notes 不会自动变成 GIS 筛选条件，也没有站点作用范围，因此不能拿它替代结构化约束。

### 4. s21：是否必须让模型把操作写两遍

不必强迫模型重复生成同一条可执行操作。当前一致性检查主要核对 hard constraints 和 preserve，并不要求每条 command 都有一条对应 operation segment。因此有 command 而没有 operation segment，本身不是危险执行的充分证据。

建议保留两种表示的用途，但把可执行操作的审计记录由本地从已校验 commands 派生。模型集中输出约束、偏好、保留要求以及无法执行的意图。不能把派生的 operation 再算成模型解析正确率，否则指标会被人为抬高。旧 operation segments 可继续读取，先保持兼容。

s21 原 gold 也有两处需要补齐：三个新增地点应分别绑定 `visit:new:1/2/3`；咖啡馆、博物馆、餐厅的细类不能只存在于 commands，而在约束评估中全部缺席。原 gold 的操作重复并不代表答案已经完整。

### 5. s14：默认 hard 是否合理

“第二站停留改为 0 分钟”是明确数值修改，“第一站不动”是明确保留，不需要额外出现“必须”才能按明确要求处理。0 分钟也是有效值，不能当作没有填写。

但不建议把所有字段默认成 hard 来制造冲突。hard 表示当前必须遵守，不能表示以后永远不能改。下一轮明确改为 45 分钟，应覆盖旧的 0 分钟；同轮同时要求两个不相容的数值，才应报告冲突。安静、轻松、最好室内等仍然应保留 soft。

操作自身的 hardness 没有独立决策价值：动作已经表达“修改什么”。短期可为兼容保留 unknown，并从操作评分中排除；hard/soft 判断集中在约束、偏好和保留要求。F7 原输出省略 hardness 后被本地填为 unknown，也不能据此断言模型主动判断了强度不明。

### 6. s20：不存在的第九站是否应保留为语义单元

应保留“想删除第九站”的意图，同时不生成可执行删除命令，并询问正确目标。模型提出问题并没有越权；当前 provider schema 也确实允许它输出 unsupported/unresolved。

不过这里更准确的是 unresolved：系统支持删除，缺的是有效目标。unsupported 应留给当前没有实现的功能。最终有效性由本地根据 Draft 站点数判定，不能仅凭模型的标签决定。

建议更新 gold，允许保存这个无效目标意图。不要因为原 gold 是空 segments，就把模型多保留了用户意图判为错误。审计记录中的 `visit:9` 不能写成有效站点 ID，也不能进入可执行动作或活动约束。

### 7. s23：understood、unresolved、unsupported 与数据库类别

当前 status 没有安排后续工作或触发数据库查询的能力。写成 unresolved 不会自动产生一次检索或核验。

建议统一按下面的含义由应用确定最终状态：

| 状态 | 含义 | 是否证明满足 |
|---|---|---|
| understood | 要求已解析，值和作用范围足够明确；例如已保存 5 分钟上限。 | 否 |
| unresolved | 还缺目标、日期或当前方案的核验证据。 | 否 |
| unsupported | 当前链路没有实现这种执行或验证能力。 | 否 |
| conflicting | 当前同时有效的要求不相容，需要用户取舍。 | 否 |
| satisfied | 有本地校验器对当前草案给出的通过证据。 | 是，但仅在证据覆盖范围内 |

“理解到了”与“不能执行”可能同时成立；单个 status 应显示当前最需要处理的障碍，解析成功另外由已通过结构检查体现。无需让模型用 status 表达整个处理流程。

command 的五个大类已经由 Category 枚举限制；细类 name/value 目前是开放字符串，未按数据库词表约束。可以让模型输出 park，但应由应用把它映射到目录真实的类型，而不是让模型猜数据库名称。

保留五大类作为召回入口，细类另做过滤。现有 Overture entity 已有 `overture.category`，A 也生成了 `search_tags`；优先复用这些字段，不要一开始只从名称猜类型。对于无标签或来源不确定的地点，保留未知状态。LLM 上下文只需要小型类型词表及本次相关证据，无需塞入全库地点。

尤其不能把 park 与 nature 判为同义。keywords 当前在列表内部按 OR 匹配，也不能用 restaurant、vegetarian 两个词同时出现于列表，就宣称素食餐厅已被严格筛选。

### 8. s24：排除博物馆、已有站点保留、规则记忆

“不要博物馆”是明确排除要求；“最好少一些博物馆”才是软偏好。完整输入还有“已有站点先别删除”，所以本轮应保留现有点位，不能自动删除所有博物馆。

建议流程：记录排除规则 → 从目录识别现有可能受影响的站点 → 展示这些站点 → 用一个问题确定替换还是只约束新候选。规则应一直保留，直到明确撤回或替换。

例如：“后续候选先排除博物馆；现有第二站是博物馆，我先保留。要替换第二站，还是只对之后新增的地点生效？”

当前 `excluded_visits` 已能识别部分冲突，strict assemble 会阻止带冲突的采用。但它没有完整表达“仅后续新增生效”的持久范围。需要用明确 scope 区分规则范围，并让冲突检查读取同一规则；不能一处按全局排除，另一处又默默放行。未明确范围前，留在 Pending 并继续展示候选。

界面应展示“已采用要求”和“本轮待采用要求”，包含类型、作用站点和未核验状态。当前 `showPrefs` 主要显示 preferred/excluded/notes，没有完整显示 active_constraints；只在请求中携带账本，用户仍看不出要求是否保留。

### 9. s24、m10：为什么模型能输出 satisfied，谁能修改它

F7 的输出限制较弱，模型把“保持不变”误写为“已经验证满足”。这是状态含义与权限混淆。它不是应用真正完成核验的证据。

当前一轮最多两次模型调用：

```text
上一轮 Draft / Preferences / Pending
→ 解释模型：输出 segments 和 commands
→ 本地格式、引用、命令一致性检查与账本合并
→ 本地检索
→ 可选的候选选择模型：只输出 candidate_key 和推荐理由
→ 本地组装预览
→ resolve 与前端采用
→ 路线计算
```

没有把同一条约束来回交给模型“自我核验”的循环。候选选择会看到 Preferences，但其输出格式只能选择候选，不能合法写回状态。下一轮解释模型会再次看到已保存的约束。

模型看见字段不等于有写入权限。应用必须用本地白名单限制输出，然后单独处理本地校验结果。当前 reducer 会把新传入的普通 satisfied 降回 understood，并把营业约束保持 unresolved，但 preserve 不写入该账本，原 interpretation 仍可能残留 satisfied；provider 输出不能仅靠共享的持久状态模型验收。

有依据的 satisfied 应来自一条本地校验结果，至少绑定约束键、校验器、结论、证据引用和草案版本；涉及目录的还要绑定目录版本。地点、时间、交通方式或路线变更后，相关证据必须失效。source=user_explicit 表示要求来自用户，不应被改成 route 来假装证明；“要求来源”和“验证来源”是两件事。

当前 B 分支的 `app/stage2b/planning.py:259` 仍返回 opening_hours_checked=False，Stage2C 预览也如此。C 的后续实现不能仅凭小组消息视作本分支已经接入；需要联调其实际输出后，再允许升级状态。

### 10. s31：模型的分段更丰富，但不能整份照抄为 gold

认可你的核心观察：模型保留了“喝咖啡”的细类，并把上午和下午的时间、区域分别拆开，比原 gold 完整。原 gold 应补上这部分。

但模型还有三个实质问题：

1. 该 fixture 的 Draft 没有站点。模型使用 `visit:1/2` 表示约束，会引用不存在的当前站点；应为 `visit:new:1/2`。
2. Bugis/Bayfront 是活动区域，却放在 place.query，变成名称、地址文本匹配，不能证明空间范围。
3. 当前 Stage2C 没有逐站时间窗口执行能力，模型没有提出相关处理问题，也没有说明能力限制。understood 不能当作已经安排到指定时段。

应保留两段活动各自的时间与区域，不把“9–11 点在此活动”擅自变成“必须停留整整两小时”。区域名称也不能擅自变成某个固定半径。若 C 已支持相应空间查询，可先接区域解析和已有 nearby 能力，再接逐段时间校验；若尚无对应能力，继续展示未核验候选并明确边界。

### 11. s32、s33：统一新加坡时间，但保留内部时区

`2026-10-28T09:00:00+08:00` 已经是东八区 09:00，不是 UTC 的 09:00。`Z` 或 `+00:00` 才是零时区。格式较技术化不等于用了错误时区。

建议界面统一显示“2026-10-28 09:00（新加坡时间）”，内部继续保留带时区的完整时间。`TimeSettings` 目前会拒绝无时区时间，并转换到 SGT；删去 +08:00 会破坏现有校验，且容易被不同浏览器按不同本地时区解释。

只给“18 点”而没有日期时，先保存时钟值，不凭系统当天日期补全。s33 模型擅自补 2026-10-27 不合适；当前 fixture 也没有出发时间。应保留截止要求并问日期与出发时间。若 Draft 已有确定日期，则可在本地复用该日期。

### 12. s42：模型补出了轻松偏好，但 null 不能表示少走路

原 gold 漏了 `pace=relaxed`，应补。模型保留了轻松、室内、少走路的意图，这一部分更好；但 `max_walk_minutes=null` 是错误数值表示。

建议规范结果包含：pace=relaxed、environment=indoor、walking_effort=low 三个偏好；add_visit 博物馆意图及 place_type=museum。室内的 scope 需按语句语境明确，不能不加规则就在 global 与新站点之间漂移。

只有“取消步行限制”才清除上限；“少走路”保留定性偏好；“最多十分钟”设置数值；未提及上限则保持原值。当前空值合并漏洞必须用已有数值上限的多轮场景测试，不能只在空白状态下看输出。

### 13. s43：对话可以自然，但不能推迟披露关键能力限制

同意不应把体验写成程序报错问答。可以先谈亲子活动，同时用一句话说明无台阶要求尚无法完整核验，例如：

“可以先按亲子活动找候选。全程无台阶的要求我已记下，但目前不能完整核验，暂时不能保证满足。孩子大概几岁，更想去室内场馆还是公园？”

不需要让用户先同意一串免责声明；但也不能寄希望于后面某轮也许再提无台阶。候选展示与最终满足要求的行程应分开判断。

`theme=family` 与 `child_suitability=true` 相关，但含义不完全相同：亲子意向并不证明地点适龄或设施合适。用户表达应规范为亲子主题，地点适龄性则需要候选证据。当前一致性检查只要有任意 question 就可能放过未处理的 hard 要求；s43 中“想去哪类地点”的问题并没有解决无台阶条件，这项检查需要修正。

## 我这边建议的实施顺序

### 15. 第一批：先堵住状态与采用错误

涉及 `frontend/stage2c/chat.js`、`operation_adapter.py`、`models.py`、`semantic.py`、`engine.py`。

- 取消候选选齐后自动采用；确认按钮只受候选与应用校验结果控制。
- 新增本地 provider 输出验收：拒绝 satisfied/catalogue/route、缺字段、空白 quote、无效 scope；保存状态的兼容读取另走明确入口。
- 明确撤回才允许清除；模糊值不再用 null 代替。账本与 Draft 参数以同一次更新结果落地。
- 不再以“questions 非空”代表每个 hard 要求已处理；逐条记录其参数支持、缺失信息或能力限制。
- can_apply 只表示能采用草案，不能表示现实约束已满足；未知 hard 条件的候选可供探索，不能自动作为满足要求的结果交付。

验收场景：找博物馆不改 Draft；选好候选仍待确认；模型伪造 satisfied 被拒；已有 10 分钟上限后说少走路，两份状态都保留 10；明确取消后两份都清除；无关的澄清问题不能解除无台阶要求。

### 16. 第二批：让细类真正控制检索

涉及 `retrieval_rules.py`、`semantic.py`、`catalogue.py`、`prompts.py`。

- 统一小型类型词表与确定性别名；park/cafe/restaurant/museum 保留为细类。
- 从作用范围明确的 segments 编译检索要求，减少让模型在 segment 和 command 中重复填相同字段。
- 粗类别用于召回，细类与已有结构化来源用于过滤，普通兴趣用于排序。未知类型证据不能被当作通过。
- 保留专名 query 与空间 anchor 的区别；nearby 的直线半径能力不能冒充步行可达。
- 每个新增站点独立编号，绑定稳定 ID 后再处理调序。范围错误不靠字符串相似度补救。

验收场景：nature 中的海滩不能仅因类别相同进入公园结果；餐厅不能退化成全部 food；素食不能因 restaurant 关键词匹配就视为通过；三新增地点的约束分别绑定；调序后仍跟随原 visit ID。

### 17. 第三批：偏好记忆、排除范围、时间和对话

涉及 `models.py`、`semantic.py`、`engine.py`、`time_updates.py`、`prompts.py` 和前端需求展示。

- 将需要跨轮保留的结构化偏好纳入确定性记忆，避免只保存在一次 Interpretation 里。当前 reducer 只处理 constraint；仅增加 preference segments 不能完成记忆功能。
- 数值、交通模式等单值字段使用明确替换；theme 等多值字段使用集合增删，不能一律采用“同名最后一个值”。
- notes 作为展示摘要，从活动要求生成或随要求同步失效，避免外带取消后仍有旧 notes。
- 排除规则明确作用于全局还是后续新增；现有冲突用站点名询问，不自行删除。
- 统一新加坡本地显示与带偏移的内部时间；缺日期或出发时间时不补造。
- 无台阶、营业等问题用一条能力说明加一个推进游玩的问题，避免一串机械确认。
- 与 C 对接明确的核验结果后才更新 satisfied；地点、日期、路线变化时让旧结果失效。

验收场景：本次咖啡偏好不污染所有后续站点；多个主题同时保留；不提及要求不等于撤销；排除博物馆不静默删已有点；18 点不补造当天日期；界面能看到活动约束和其未核验状态。

### 18. 字段只在有必要时增加

不为每条意见都加字段。操作 hardness 可以保留兼容而不参与决策；understood/unresolved 不再增加另一套同义状态。需要考虑的新增或扩展仅限以下实际缺口：

| 字段或结构 | 原因与必要性 | 限制 |
|---|---|---|
| 明确更新动作 set/clear | null 当前混淆未知与撤回，会误删记忆。 | 仅用于需要更改的结构化要求；旧 null 撤回只在明确撤回证据下兼容。 |
| 持久要求的 kind | 当前 ActiveConstraint 无法区分约束与结构化偏好，coffee/pace 等不能靠自由文本 notes 完整记忆。 | 可复用 segment.type 的含义；旧记录默认 constraint，避免重复定义。 |
| 本地核验记录 | satisfied 必须回答由谁、根据什么、对哪份草案判断。 | 由应用写入，模型只能读取；要求来源仍保留 user_explicit。 |

核验记录的最小内容：约束键用于对应要求，validator 标识判断代码，result 表示通过/失败/未知/不支持，evidence_ref 指向实际证据，draft revision 防止旧方案证据复用；使用目录时带 catalogue build ID。只有具有时间敏感性的证据才额外需要核验时间。不能把“字段写了 route”当作路线证据。

优先使用现有字段：类型来自 segments 的 name/value，范围来自 scope，顺序来自 command.order，站点身份来自 visit ID。暂不新增独立搜索工作流、向量数据库、自动修 JSON 模型或多轮自我核验代理。

### 19. 第四批：修订标注与评估，再决定是否跑新实验

涉及 `tests/fixtures/`、`evaluation.py`、评估说明与报告。

1. 先写出修订规范与每条答复。保留你的原始复核，另记录规范版本和改动理由；revise/discuss 不自动提升为 human_reviewed。
2. keep 可以作为确认依据，但发现确实遗漏的语义仍单独列出，例如 s01 空间参照与 s21 细类，不悄悄更改你的决定。
3. 允许可证明的格式等价：单个新增的 visit:new 与 visit:new:1、相同实际时刻的时区表示。禁止把 park 与 nature、亲子意向与已验证适龄性当作等价。
4. 分开报告语义内容、命令目标、记忆状态、候选检索、能力边界与对话质量。操作派生记录、notes 字面差异不应主导语义 F1；细类丢失、错误 scope、错误撤回、虚假验证仍然必须扣分。
5. 澄清评估不只判断有没有问号，应检查是否处理关键缺口、是否保留所有明确要求。另做完整候选→确认→路线检查，原解析实验没有覆盖这些步骤。
6. 现有 71 轮继续作为已见开发集，先离线重放和做确定性回归。后续补英文及混合语样本；真正独立的最终测试应在未见模型输出时先定答案，再冻结。
7. 新指标不能替换 F7 原报告。保留模型版本、prompt/wire、标注版本和评分规则，解释变分来自答案修正、检查器变化还是新模型输出。

第一至三批的验收先用本地测试完成；新一轮真实模型实验另行确定版本、样本和调用上限。本轮分析没有使用之前已用满的 71 次调用额度。

## 你要做什么

暂不需要把剩余 46 个话轮全部补标，也不需要把模型答案整份复制到 gold。先对照第 3、8、10、13 节审阅产品行为：候选确认、已有博物馆的处理、分时段请求的保留方式、无台阶要求的表达。待规范确定后，再将 revise/discuss 整理成可导入的结构化答案。
